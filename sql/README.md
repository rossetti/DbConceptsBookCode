# SQL scripts

PostgreSQL scripts that build the book's database: HG Industries, a maker of
hand trucks and garden carts, seen from its distribution, production, and
quality departments. Each department is a schema of one database. The
scripts run on their own in DataGrip, DBeaver, or psql, and ship with the
rendered book as downloads.

## Loading the database

Create an empty database once (the book uses `dbconcepts`), then open and run
**one** file from `load/`:

| To have the database as it stands at stage | Run |
|---|---|
| D1, customers only | `load/through-d1.sql` |
| ... | ... |
| Q, the base data of every schema | `load/through-q.sql` |
| G, the base data and a year of history | `load/through-g.sql` |
| S, all of the above and the sales star schema | `load/through-s.sql` |

Each `load/through-<stage>.sql` deletes the book's schemas and rebuilds them
through that stage, so it can be run again at any time to get back to a known
state. It touches no other schema.

From a terminal:

```sh
psql -d dbconcepts -f load/through-q.sql
```

## The stages

The database is introduced one idea at a time. Each stage script adds its
tables and rows to the stages before it:

| Stage | Script | Adds |
|---|---|---|
| D1 | `distribution/d1-customer.sql` | `customer` |
| D2 | `distribution/d2-customer-order.sql` | `customer_order` |
| D3 | `distribution/d3-product-order-line.sql` | `product`, `order_line` |
| D4 | `distribution/d4-warehouse-stock-level.sql` | `warehouse`, `stock_level` |
| D5 | `distribution/d5-shipment.sql` | `shipment`, `shipment_line` |
| P1 | `production/p1-part.sql` | `part`, `manufactured_part`, `purchased_part`; connects `distribution.product` to production |
| P2 | `production/p2-bom-line.sql` | `bom_line`, the bill of materials |
| P3 | `production/p3-routing.sql` | `work_center`, `machine`, `operator`, `certification`, `operation`, `work_order` |
| Q | `quality/q-inspection.sql` | the `quality` schema |
| G | `history/g-history.sql` | a year of history: 22 more customers, 602 orders from April 2026 to March 2027 with their lines and shipments, and six months of inspections (generated; see below) |
| S | `sales/s-star-schema.sql` | the `sales` star schema: `order_line_fact` and the `date_dim`, `customer_dim`, and `product_dim` dimensions, built from distribution and production by the script itself (an ETL process in SQL) |

A stage script assumes the stages before it were loaded into a freshly reset
database: rows are inserted in a fixed order, so every surrogate key is known
(the first customer is 1), and foreign keys are written as those numbers.
`reset.sql` removes the book's schemas.

## Other scripts

Scripts that are not stages run against a stage that is already loaded, and
say which in their opening comment:

- `documents/`: HG Industries' orders as JSON documents in PostgreSQL, for the
  book's appendix on NoSQL databases. `order-document.sql` builds one order's
  document; `order-documents.sql` stores every order of stage D5 as a document
  and queries them.
- `embedded/`: the stock tables in SQLite and DuckDB, for the appendix on
  embedded databases; run with those databases' own shells.

## Conventions

- Tables named in the singular; a primary key column `<table>_pk`, generated
  as an identity; a foreign key column `<referenced table>_fk`, or named for
  its role (`bom_line.assembly_fk`, `component_fk`).
- The business identifier (`customer_number`, `part_number`) is its own
  `UNIQUE` column, and so is a key made of several columns
  (`UNIQUE (customer_order_fk, line_number)`).
- Every script opens with a comment saying what it adds and what it requires.
- A script cites the book, if at all, by label (`@sec-q-outer-joins`), never
  by a rendered number. `scripts/check-code-refs.sh` enforces this.
- **No exercise answers here.** This directory is public; the answers to the
  book's exercises are not distributed with it.

## For the author: editing the scripts

The commands in this section run in the book's source repository, which is
not public; readers need none of them. The stage scripts are the source.
`load/` is generated from them:

```sh
python3 scripts/build-sql-loads.py           # regenerate load/ after editing a stage
python3 scripts/build-sql-loads.py --check   # fail if load/ is stale
python3 scripts/test-sql.py                  # load every stage and check its data
```

Stage G is generated by `dbconcepts.history.GenerateHistory` in the companion
code project, from seeded KSL random number streams, so it is the same on
every run:

```sh
scripts/build-history.sh           # regenerate history/g-history.sql
scripts/build-history.sh --check   # fail if the committed file is not what the program writes
```

`test-sql.py` loads the database stage by stage into `dbconcepts` and checks
each data feature the chapters rely on, such as the customer who never
ordered, the backorders, and the axle diameter that drifts out of
specification. Change the data and a check fails until the chapter and the
check agree.
